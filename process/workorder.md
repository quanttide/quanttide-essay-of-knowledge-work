# 可溯源的工作订单

我们抛开代码和术语，用一个生活里的例子从头讲。

## 先讲一个类比：外卖订单

你在 App 上点外卖，订单页面上会显示一条条记录：
```
14:00  商家已接单
14:05  商家开始制作
14:20  骑手已取餐
14:35  已送达
```
现在想一个问题：
**App 怎么知道这个订单“已送达”？**

### 笨办法（传统做法）

给订单存一个“状态”字段，每次直接改它：
```
状态: “配送中”  →  改成  →  状态: “已送达”
```
改完之后，前面发生的事就没了。如果骑手和你说好放门口但你没收到，你去找客服，客服**查不到中间发生了什么**——因为那个字段被改来改去，历史丢了。

### 聪明办法（这份代码的做法）

**从来不改状态，只往流水里加新记录：**
```
14:00 商家接单        ← 永远保留
14:05 开始制作        ← 永远保留
14:20 骑手取餐        ← 永远保留
14:35 已送达          ← 永远保留
```

至于“现在到哪一步了”？**不用存，看最后一条就知道**。
出了纠纷，完整过程全都查得到。这就是那句“**改结论的方式不是改状态，而是追加一条新流水**”。

## 对应到代码，其实只有三个动作

忘掉那些名词，这个 `Task` 类型就是一张**外卖订单**：

```rust
pub struct Task {
    pub workflow_name: String,  // 我点的是什么套餐（流程）
    pub start: String,          // 从哪一步开始做
    pub journal: Vec<JournalEvent>,   // 【流水】上面那种时间线记录
    pub gates: Vec<String>,     // 【待确认】需要你点“同意”的弹窗
    pub artifacts: BTreeMap<String, String>,  // 【声明】最终交付物放在哪
}

```

代码里所有操作，翻来覆去就两个：

**动作一：`recorded` = 往时间线加一条记录**
```rust
task.recorded(“14:35”, “送达”, “放在门口”, true);
```
就像往订单时间线里追加一行。**只加，不改旧的**。

**动作二：`with_gates` = 往“待办”清单里加一条**

```rust
task.with_gates(&[”这一步我不确定，需要人确认“.to_string()]);
```

就是程序遇到没把握的事，**自己不敢下结论，先记下来等人来看**。相当于外卖 App 弹窗问你”放门口可以吗？“——而不是替你回答”可以”。
就这两个动作，没了。

## 那段话到底在担心什么？

现在说背景。这份代码是给 **AI 智能体**干活用的。
传统软件干活，出了 bug 跑个测试就知道了。但现在是一个 **AI** 在干活，它给你写了一份报告——你敢直接用吗？
你心里会冒出这些问题：
- 它是**照着哪份规范**写的？
- 中间有没有**人**检查过？
- 它有没有**自作主张**跳过步骤？
如果 AI 干活像传统程序那样改状态字段，这些问题的答案就**丢了**，你只能选择信或不信。
但有了流水，你可以翻账本：
```
10:00  开始执行「写报告」步骤
10:05  ⚠️ 闸门：报告结论有歧义，等人确认     ← 人来了，确认了
10:10  继续执行
10:30  完成，产物在 reports/xxx.md
```
一目了然：哪步是人拍板的、哪步是 AI 自己走的、最终产物在哪。

## 所以一句话总结

> **像记外卖物流一样记录 AI 的每一步工作，只加不改，事后随时能查清“它是怎么干完这个活的”。**
那段话里所有高深的词——事件溯源、账货分离、信任域——说的都是这一件事的不同侧面：
- **只加不改** → 历史查得到（“账“）
- **产物单独放** → AI 说”我写好了”和实际文件是两回事，要分开验证（“货“）
- **不确定就停** → AI 不能自己给自己盖“通过”章（”闸门“）
